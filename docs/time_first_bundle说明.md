# Time First Bundle 调度策略说明

## 1. 一套硬编码策略

- 先保住快超时的任务（时间优先）
- 能两单一起做就尽量拼单（提高吞吐）
- 在不影响派单的前提下，让空闲车补电（充电再平衡）

---

## 2. 它在系统里怎么工作

每个 tick，系统会先更新世界状态，再调用策略输出车辆计划。

- 输入：`StrategyContext`
  - 当前时刻、路网最短路查询器、车辆状态、任务状态、充电站状态、全局参数
- 输出：`Dict[int, VehiclePlan]`
  - 对每辆车给一个关键节点序列（`planned_path`）和动作序列（`action`）

注意：策略只负责“关键节点级别”的决策（例如仓库 -> 任务点 -> 充电站），具体逐边行驶由 `world.py` 继续展开执行。

---

## 3. 调度总流程（按阶段）

## 3.1 阶段A：先处理不在仓库的空闲车

如果空闲车不在仓库：

1. 若电量低于低电阈值，先派去最近且可达的合适充电站；
2. 否则先让它回仓（`keep` 到仓库）。

这样做的目的，是让“可用于接单的车”尽量集中在仓库，避免后面派单时车都散在外面。

## 3.2 阶段B-1：优先派紧急任务（单任务）

先从待处理任务中识别紧急任务，再逐个分配车辆：

- 紧急任务定义：剩余截止时间已经接近“最短可完成时间 + 动态缓冲”
- 每个紧急任务只先按单任务派发（仓库 -> 任务点 -> 仓库）
- 车辆选择时要同时满足：
  - 能装下该任务重量
  - 电量安全校验通过
  - 在候选车里预计完成更快、能耗需求更低

这一阶段的核心是“先止损”：先防止任务直接超时爆炸。

## 3.3 阶段B-2：非紧急任务尝试拼单

对剩余非紧急任务做两两组合，寻找可行拼单方案。每个“车-任务对”会比较三种模式：

- `mode1`：第一单送完回仓，再送第二单回仓
- `mode2`：第一单后先去充电站补电，再回仓拿第二单
- `mode3`：两单送完后再去充电站补电，然后回仓

选择逻辑：

1. 过滤不可行方案（超载、能量不安全、绕路过大）
2. 对可行模式计算代价
3. 取代价最低模式，形成该“车-任务对”的最佳候选
4. 全局再从候选集合中选当前最优分配并落地，循环直到不能再拼

其中“当前最优”优先级是：

1. 可行模式数量更少的任务对优先（先处理选择空间最窄的）
2. 代价更低优先
3. 截止时间余量更小（更紧）优先

## 3.4 阶段B-3：拼单等待过久则单任务兜底

有些非紧急任务可能一直拼不上。策略维护了每个任务的等待 tick：

- 若等待时长达到 `bundle_wait_escape_ticks`，允许从拼单池“逃逸”
- 按单任务规则直接派发

这个机制避免任务长期卡在“等拼单”的状态。

## 3.5 阶段C：对剩余空闲车做充电再平衡

当车辆没被派去送任务时，策略会根据任务压力决定是否主动补电：

- 有任务压力（待处理/紧急任务存在）：
  - 只给低电车辆安排充电，保留更多可立即出车能力
- 无任务压力：
  - 对部分空闲车主动充电，保持下一波任务来时的健康电量

本质是平衡两件事：现在就能派车 vs 下一轮不会因为低电掉链子。

## 4. 关键规则

## 4.1 紧急任务

策略先估计任务最理想完成时长（去程 + 回程 + 装卸），记为 `direct_eta`。

若：

`剩余时间 <= direct_eta + dynamic_margin`

就认为是紧急任务。这里 `dynamic_margin` 会随着任务积压增加而增大。  
意思是：任务越拥堵，越要提前把任务当“紧急”处理，避免后面来不及。

## 4.2 任务优先级分层

单任务排序不是只看 deadline，而是分层：

1. 未超时任务（尤其临近截止）优先
2. 轻度超时任务（还有机会止损）次之
3. 重度超时任务放后

同层内再优先照顾“等待更久”的任务，避免饥饿。

## 4.3 拼单三模式的代价怎么比

对于可行模式，成本由三部分组成：

- 额外路程成本（绕路越多越差）
- 排队压力成本（站点压力越大越差）
- 能量风险成本（越接近电量边界越差）

代价接近时，策略会偏向模式编号更小（更保守、更稳定）的方案，减少抖动。

## 4.4 电量安全校验为什么“严格”

它不是只检查“够不够到下一站”，而是逐段检查：

1. 当前边能不能走完；
2. 走完这条边后，至少还要留出到“仓库或最近充电站”的保底电量；
3. 额外留 `reserve_energy` 安全余量。

这样可以明显减少“走到半路才发现没电”的失败情况。

## 5. 关键参数解释与调参建议

## 5.1 时间与任务相关

- `emergency_margin_ticks`
  - 越大：越早把任务判为紧急，超时率通常下降，但可能压缩拼单机会。
- `backlog_margin_gain` / `backlog_margin_cap`
  - 控制“积压时紧急阈值抬升”的力度和上限。
- `bundle_wait_escape_ticks`
  - 越小：任务更快从拼单等待转单发，平均等待时间下降，但拼单率下降。

## 5.2 拼单相关

- `enable_bundle_dispatch`
  - 是否开启拼单主流程。
- `max_detour_ratio`
  - 限制为了充电而绕路的容忍度，越小越保守。
- `w_travel / w_queue / w_energy`
  - 分别控制“路程、排队、能量风险”三种代价的权重。
- `cost_epsilon`
  - 代价近似相等时触发稳定性偏好，减少模式频繁切换。

## 5.3 充电再平衡相关

- `keep_idle_ratio`
  - 无任务时保留多少空闲车不被过度拉去充电。
- `all_low_battery_ratio`
  - 当全队都偏低电时触发更保守的保留策略。
- `depot_charge_ratio_no_pressure`
  - 无任务压力下，空闲车低于该比例会倾向补电。
- `reserve_energy`
  - 安全电量缓冲，越大越稳健，但可行路径会变少。

## 5.4 实操调参建议（中/大规模）

- 如果超时率高：先提高 `emergency_margin_ticks`，再略降 `bundle_wait_escape_ticks`。
- 如果总里程偏高：先降低 `max_detour_ratio`，再减小 `w_travel` 外的激进系数。
- 如果常出现电量相关失败：增大 `reserve_energy`，并提高低电触发阈值。
- 如果任务吞吐不足：提高拼单机会（适当增大 `bundle_wait_escape_ticks`，并检查载重约束是否过紧）。

## 6. 优点、局限与适用场景

## 6.1 优点

- 逻辑清晰，便于解释给队友和老师；
- 同时考虑时间、载重、电量、充电站压力；
- 对中等规模动态任务有较好稳定性；
- 可通过参数做针对性优化。

## 6.2 局限

- 仍是局部启发式，不保证全局最优；
- 参数较多，跨规模迁移时需要重新标定；
- 主要是“两单拼单”，更复杂协同（多车协作、多任务链）能力有限。

## 6.3 适用场景

- 课程项目的主策略或可解释基线；
- 需要“效果 + 可讲清楚”的场景；
- 作为后续 RL/元启发式策略的对照组。

---

## 7. 一句话总结

`time_first_bundle` 的核心思想是：先保时间、再提吞吐、最后稳电量。  
它追求的是“稳健可解释的高可用调度”，不是理论最优，但非常适合工程化落地与课程展示。
